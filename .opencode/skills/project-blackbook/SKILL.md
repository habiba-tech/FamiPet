# Project Black Book

Create a complete formal academic black book for a software project.

The skill is **project-agnostic**. Never assume a particular domain, technology stack, architecture, feature set, user role, or project structure.

The actual project repository, verified documentation, tests, approved proposal, and available project artifacts determine the report content.

The skill determines the academic structure, documentation quality, diagram requirements, visual organization, and formatting rules.

The black book must explain the project primarily through a balanced combination of:

* concise technical explanation
* diagrams
* tables
* workflows
* figures
* actual implementation evidence
* actual test cases
* screenshots where available and appropriate

Do not produce a text-heavy report when a concept can be communicated more clearly through a diagram, table, workflow, or figure.

---

# 1. SOURCE OF TRUTH

Before generating the black book, inspect the project thoroughly.

Inspect, where applicable:

* Repository structure
* README and project documentation
* AGENTS/instruction files
* Source code
* Backend
* Frontend
* APIs
* Database schema/models
* Relationships
* Authentication and authorization
* User roles
* Core workflows
* Background jobs
* Queues
* Workers
* External integrations
* Configuration
* Infrastructure/deployment
* Tests
* Test configuration
* Existing diagrams
* Existing screenshots
* Approved project proposal
* Existing project documentation

Use actual implementation as the primary technical source of truth.

Do not assume that something exists merely because it is mentioned in documentation or a proposal.

When documentation and implementation disagree, investigate and represent the verified current implementation accurately.

---

# 2. NO FABRICATION

Never invent:

* Features
* Modules
* Technologies
* Architecture
* APIs
* Database entities
* Relationships
* User roles
* Workflows
* Security mechanisms
* AI functionality
* Integrations
* Test cases
* Test results
* Performance numbers
* Statistics
* Screenshots
* Dates
* Milestones
* Deployment details
* References
* User counts
* Results
* Project outcomes

Do not present planned or future functionality as implemented.

Clearly distinguish:

* Implemented
* Partially implemented
* Planned
* Future scope

Only verified implementation may be described as existing functionality.

---

# 3. ACADEMIC PURPOSE

The black book must demonstrate the project through its:

* problem and objectives
* requirements
* scope
* analysis
* system design
* architecture
* workflows
* core functionality
* data model
* implementation
* testing
* development process
* results/observations where actual evidence exists
* conclusion and future scope

The report should be suitable as formal academic project documentation.

Do not turn it into:

* a programming tutorial
* an API reference
* source-code documentation
* a generic textbook
* a collection of endpoint lists
* repetitive prose
* artificial content created only to increase page count

---

# 4. EVALUATION-AWARE DOCUMENTATION

The official project evaluation includes:

* Documentation
* Quality
* Working
* Presentation
* Viva

The black book should therefore provide clear factual evidence that helps a reviewer understand:

* what was developed
* why it was developed
* how it is designed
* how it works
* how important functionality operates
* how the implementation is structured
* how it was tested

Do not fabricate evidence to satisfy evaluation criteria.

Do not assign marks, scores, rankings, or claims of quality to the project.

---

# 5. DOCUMENT STRUCTURE

The generated black book must begin with:

1. Table of Contents
2. List of Figures
3. List of Tables, when applicable
4. Project chapters
5. References
6. Glossary, when applicable
7. Appendices, when applicable

The following institutional sections are outside the generated project-focused black book and should not be generated by this skill:

* Title Page
* Certificate
* Declaration
* Acknowledgement
* Approved Project Proposal
* Plagiarism Report
* Institutional approval pages

These may be added manually.

---

# 6. CHAPTER STRUCTURE

Do NOT use a hardcoded chapter list.

Analyze the actual project and create a logical academic chapter structure.

The chapters should form a clear progression from understanding the problem to understanding the implemented system.

A suitable progression may include concepts such as:

* Introduction
* Problem and Objectives
* Requirements and Scope
* Analysis
* System Design
* Architecture
* Core Features
* Data Management
* Implementation
* Testing
* Development Process
* Conclusion and Future Scope

These are examples only.

The final chapter structure MUST be derived from the actual project.

You may:

* combine chapters
* split chapters
* rename chapters
* add project-specific chapters
* remove irrelevant concepts
* reorder chapters

Do not create chapters merely to increase report length.

---

# 7. CONTENT-FIRST, NOT TEXT-FIRST

The black book must NOT be predominantly long paragraphs.

For every major concept, determine the clearest presentation method.

Prefer, where appropriate:

* Diagram + short explanation
* Workflow + short explanation
* Architecture diagram + explanation
* Data model/ER diagram + explanation
* Sequence diagram + explanation
* Activity diagram + explanation
* Use-case diagram + explanation
* State/lifecycle diagram + explanation
* Component/deployment diagram + explanation
* Process diagram + explanation
* Table + concise explanation
* Screenshot + explanation
* Test-case table + explanation

Use paragraphs only where textual explanation is actually required.

Avoid explaining a complex process entirely through several paragraphs when a proper diagram can communicate it more clearly.

---

# 8. DIAGRAMS ARE A REQUIRED MAJOR COMPONENT

Diagrams are NOT optional decoration.

The black book MUST use diagrams extensively wherever the actual project provides information that can be represented visually.

Analyze the project and identify all major concepts that should be represented using diagrams.

Create project-specific diagrams based on the actual implementation.

Potential diagram categories include, but are not limited to:

* System/context diagram
* Process model
* Project workflow
* System architecture
* Deployment architecture
* Component diagram
* Module/dependency diagram
* Data-flow diagram
* Use-case diagram
* Class diagram
* Object diagram
* ER/data model diagram
* Activity diagram
* Sequence diagram
* State/lifecycle diagram
* Authentication/authorization flow
* Core feature workflow
* Background job/queue workflow
* AI/processing pipeline
* Integration flow
* Infrastructure/network diagram
* Other project-specific technical diagrams

This is NOT a fixed checklist.

Select diagrams according to the actual project.

However, do not omit a conventional diagram when the project contains enough verified information to create it accurately.

**Skip a diagram only when it is genuinely not applicable to the project or technically impossible to derive accurately from the available project evidence.**

Do NOT skip a useful diagram merely because:

* it is complex
* it requires deeper repository analysis
* the project has many components
* creating it requires tracing multiple modules
* it requires inspecting database relationships
* it requires following an asynchronous workflow

The repository must be analyzed deeply enough to create accurate diagrams.

---

# 9. DIAGRAM QUALITY

Every diagram must be:

* project-specific
* technically accurate
* readable
* academically appropriate
* clearly labelled
* consistent with the implementation
* useful for explaining the system

Never create generic diagrams such as:

`User → System → Database`

when the actual project contains enough information to create a meaningful project-specific diagram.

Do not create decorative diagrams that provide no technical information.

Do not overload one diagram with unrelated concepts.

One diagram should have one clear purpose.

---

# 10. DIAGRAM SELECTION

For every major chapter, ask:

> Can an important concept in this chapter be communicated more effectively using a diagram?

If yes, create and include the appropriate diagram.

Examples:

Architecture chapter → architecture/component/deployment diagram.

Data chapter → ER/data model diagram.

Authentication chapter → authentication/session/authorization flow.

Feature chapter → feature workflow/activity/sequence diagram.

Async processing chapter → queue/worker/job flow.

User interaction chapter → use-case/activity/sequence diagram.

Infrastructure chapter → deployment/network diagram.

Development process → process model/Gantt/timeline where actual information exists.

Do not force diagrams into concepts where they provide no value.

---

# 11. DIAGRAM INTEGRATION

Every included diagram must have:

* Figure number
* Descriptive caption
* Diagram
* Short explanation immediately following it

The explanation must describe what the diagram represents and how it relates to the actual implementation.

Do not place a diagram in the report without explaining it.

Do not explain a diagram using information that is not supported by the project.

Use the `project-diagrams` skill when creating technical diagrams.

The black book decides which diagrams are required.

The diagram skill is responsible for creating technically accurate diagrams.

---

# 12. TABLES

Use tables when they communicate structured information better than prose.

Appropriate examples include:

* Functional requirements
* Non-functional requirements
* User roles and permissions
* Technology stack
* Module responsibilities
* Database entities
* Feature comparison
* Test cases
* Development timeline
* Configuration information
* System components

Do not create unnecessary tables merely for visual variety.

All table content must be based on actual project evidence.

---

# 13. SCREENSHOTS

Use real screenshots when they materially help explain the implemented system.

Screenshots must come from the actual project.

Do not generate fake application screenshots.

Do not use screenshots merely to fill pages.

Each screenshot should have:

* Figure number
* Caption
* Short explanation

Use screenshots primarily for important user-facing functionality and workflows.

---

# 14. FEATURE EXPLANATION

Major features must be explained rather than merely listed.

For each significant feature, explain the relevant combination of:

1. Purpose
2. User/actor
3. Workflow
4. Inputs
5. Processing
6. Data involved
7. Validation
8. Security/permissions where applicable
9. Background processing where applicable
10. Output/result
11. Relevant implementation
12. Test evidence
13. Diagram where appropriate

Do not list endpoints as the primary explanation of a feature.

Endpoints may be mentioned when technically relevant, but they must support the explanation rather than replace it.

---

# 15. ARCHITECTURE

The architecture must be explained according to the actual project.

Determine whether the project uses:

* monolith
* modular monolith
* microservices
* client-server
* serverless
* event-driven architecture
* layered architecture
* another architecture

Do not force terminology that does not match the implementation.

Where the architecture contains meaningful components, create an architecture diagram.

Explain:

* major components
* responsibilities
* communication
* data flow
* external services
* background processing
* storage
* important boundaries

Use a diagram as the primary visual explanation whenever practical.

---

# 16. DATABASE AND DATA

Inspect the actual database implementation.

Where sufficient relational/data-model information exists, create an appropriate data diagram.

This may include:

* ER diagram
* conceptual data model
* logical data model
* entity relationship explanation
* relevant schema diagram

Explain important:

* entities
* relationships
* keys
* constraints
* important data structures

Do not blindly convert every database table into a diagram if that produces an unreadable result.

Split diagrams when necessary.

---

# 17. WORKFLOWS AND SEQUENCES

Important workflows must be visually represented whenever the project provides enough evidence.

Examples include:

* authentication
* registration
* major CRUD workflow
* examination workflow
* content workflow
* AI processing
* asynchronous jobs
* notifications
* approval workflows
* file processing
* background workers
* user-specific workflows

Use the appropriate diagram type rather than forcing every workflow into the same diagram style.

---

# 18. TESTING

Testing must be based on actual project evidence.

Inspect:

* unit tests
* integration tests
* end-to-end tests
* API tests
* test scripts
* fixtures
* test configuration
* assertions
* documented manual tests
* actual validation results

Do not invent test cases.

Do not claim a test passed unless there is evidence that it passed.

Present relevant actual test cases using clear tables and explanations.

A test-case table may include:

| Test ID | Feature/Scenario | Input/Condition | Expected Result | Actual Result | Status |

Only populate fields supported by evidence.

If actual test evidence does not exist, state that clearly rather than fabricating results.

---

# 19. DEVELOPMENT PROCESS AND GANTT CHART

Include development-process documentation when supported by the available project information.

A Gantt chart should be included when reliable timeline information exists or when the academic requirements require one.

Possible sources include:

* documented project timeline
* approved proposal timeline
* verified development schedule
* project planning documents

Do not invent dates.

Do not automatically convert Git commit history into a Gantt chart unless that accurately represents the project's planned/development timeline.

---

# 20. REFERENCES

Use academically appropriate references.

Do not invent references.

References may come from:

* approved proposal
* verified project documentation
* actual technologies/framework documentation
* relevant academic literature
* authoritative technical sources

Use the required academic citation style where specified by the institution, such as IEEE or Springer.

---

# 21. GLOSSARY

Include a glossary when the project contains significant technical terminology that benefits from explanation.

Use actual terminology from the project.

Keep definitions concise and accurate.

---

# 22. FORMATTING — STRICT

The black book MUST be strictly black-and-white.

No colored pixels should be intentionally produced anywhere in the document.

This applies to:

* text
* headings
* tables
* diagrams
* figures
* captions
* links
* borders
* backgrounds
* page decorations
* charts
* code blocks
* generated graphics

Use black, white, and grayscale only.

---

# 23. TYPOGRAPHY

Use:

* 12 pt Times New Roman
* Single line spacing

Chapter headings:

* 20 pt Times New Roman
* Bold
* ALL CAPS
* Centered

Maintain a formal academic appearance throughout.

Do not use colorful modern-report styling.

Do not use decorative typography.

---

# 24. HYPERLINKS

Links MUST NOT appear colored.

Use:

```latex
\usepackage[hidelinks]{hyperref}
```

Do NOT use:

```latex
colorlinks=true
```

Do not introduce colored hyperlink borders or link styling.

---

# 25. PAGE LAYOUT

Use a binding-aware two-sided layout.

Unless an official institutional requirement specifies different dimensions, use approximately:

* Inner margin: 1.30 in
* Outer margin: 0.90 in
* Top margin: 0.90 in
* Bottom margin: 0.90 in

The inner margin must be larger to account for binding.

Use a proper two-sided document layout.

---

# 26. PAGE NUMBERS

Page numbers MUST appear at the bottom of the page.

For two-sided printing:

* Odd/right-hand pages → bottom-right
* Even/left-hand pages → bottom-left

Do not place page numbers at the top.

Chapter-opening pages must have no visible page number.

The chapter-opening page still counts toward pagination.

---

# 27. CHAPTER OPENING PAGES

Every chapter MUST begin on a new right-hand/odd page.

The first page of every chapter must contain ONLY:

* Chapter number
* Chapter title
* Short chapter description

Nothing else.

Do NOT place on the chapter-opening page:

* paragraphs
* tables
* diagrams
* figures
* screenshots
* lists
* code
* captions
* page numbers
* headers
* unrelated content

Actual chapter content begins on the following page.

If a blank page is required to force the chapter onto a right-hand page, that page must be genuinely blank:

* no text
* no page number
* no header
* no footer
* no decoration

---

# 28. PAGE COMPOSITION

Do not cram content to reduce page count.

Do not leave large unexplained empty areas when content can be organized naturally.

Figures and diagrams must be sized for readability.

Do not shrink diagrams until labels become unreadable.

Large diagrams may occupy a dedicated page when necessary.

Tables may occupy dedicated pages when necessary.

A diagram-heavy chapter is acceptable and encouraged when the project warrants it.

The goal is a professional academic report, not minimum page count.

---

# 29. VISUAL BALANCE

The report must visually balance:

* concise explanations
* diagrams
* figures
* tables
* screenshots
* structured lists

Avoid:

* walls of text
* repetitive paragraphs
* huge empty pages
* oversized headings
* tiny diagrams
* decorative graphics
* irrelevant images
* excessive bullet lists

Use visuals to improve technical understanding, not decoration.

---

# 30. FIGURE AND TABLE NUMBERING

Number figures consistently throughout the document.

Number tables consistently throughout the document.

Every figure must have a caption.

Every table must have a title/caption.

References to figures and tables in the text must use their correct numbers.

Do not manually create inconsistent numbering.

Use LaTeX automatic numbering and references where possible.

---

# 31. CODE

Code is supporting evidence, not the main content.

Include code only when a small snippet materially explains an important implementation decision.

Do not dump source files into the black book.

Do not fill pages with code.

Prefer diagrams, explanations, tables, and workflows over large code listings.

---

# 32. REFERENCES BETWEEN SECTIONS

Maintain logical continuity.

A feature introduced in one chapter should be referenced consistently in later chapters.

Use consistent terminology for:

* actors
* modules
* components
* entities
* services
* workflows
* technologies

Do not rename the same project component arbitrarily between chapters.

---

# 33. PROJECT DIAGRAM GENERATION

When diagrams are required:

1. Identify the concept.
2. Inspect the repository for evidence.
3. Select the most appropriate conventional diagram type.
4. Create the diagram from actual implementation.
5. Validate its technical correctness.
6. Validate readability.
7. Render it in black-and-white/grayscale.
8. Add it to the appropriate chapter.
9. Add figure numbering and caption.
10. Add a concise explanation.

Use the `project-diagrams` skill for diagram creation and validation.

Do not create diagrams first and then invent explanations around them.

---

# 34. EXISTING BLACK BOOK

If an existing black book exists:

* inspect it
* reuse accurate content where appropriate
* identify outdated sections
* update incorrect content
* preserve useful verified material
* improve structure and visual presentation

Do not blindly preserve incorrect or outdated content.

Do not create a competing second black book.

---

# 35. MISSING INFORMATION

Never use placeholders such as:

* `[PLACEHOLDER]`
* `<PROJECT NAME>`
* `TBD`
* `TODO`

for final required information.

If mandatory academic information is missing:

1. Ask the user for it.
2. Do not invent it.
3. If the user explicitly chooses to continue without it, leave the field blank.
4. Report the missing information after generation.

---

# 36. LATEX REQUIREMENTS

Use LaTeX for the black book.

Prefer XeLaTeX when Times New Roman and reliable Unicode support are required.

Use:

* proper document structure
* automatic table of contents
* automatic figure numbering
* automatic table numbering
* cross-references
* bibliography management
* proper two-sided layout
* appropriate page-break control

Do not manually fake page numbers or figure numbers.

---

# 37. OUTPUT STRUCTURE

Use:

```text
docs/blackbook/
├── main.tex
├── references.bib
├── sections/
├── figures/
├── tables/
├── appendices/
└── output/
```

Keep source files organized.

Keep generated PDF/output files under `output/`.

---

# 38. COMPILATION

Compile using XeLaTeX/latexmk.

Preferred command:

```bash
latexmk -xelatex -interaction=nonstopmode main.tex
```

Resolve compilation errors before completion.

Do not consider the black book finished merely because the `.tex` files were generated.

---

# 39. FINAL VALIDATION

Before finishing, validate all of the following.

### Content

* Project is accurately represented.
* Chapters are logically organized.
* Features are actually implemented.
* Technical claims are supported.
* No fabricated information exists.
* Testing is based on actual evidence.
* References are valid.

### Diagrams

* Major applicable concepts have diagrams.
* Diagrams are project-specific.
* Diagrams are technically accurate.
* Diagrams are readable.
* Diagrams are explained.
* No useful diagram was omitted without a valid reason.

### Formatting

* Strict black-and-white output.
* No colored links.
* Times New Roman.
* 12 pt body text.
* Single spacing.
* 20 pt bold ALL-CAPS chapter headings.
* Binding-aware margins.
* Two-sided layout.
* Correct bottom page numbering.
* Odd/right chapter starts.
* Dedicated chapter-opening pages.
* No visible page number on chapter-opening pages.
* Genuine blank forcing pages.
* Correct figure numbering.
* Correct table numbering.
* Correct table of contents.
* Correct list of figures.
* Correct list of tables.

### Visual quality

Inspect the compiled PDF, not only the source.

Check for:

* unreadable diagrams
* cropped figures
* overflowing tables
* bad page breaks
* excessive whitespace
* cramped content
* orphaned headings
* incorrect chapter starts
* incorrect page numbers
* colored elements
* inconsistent typography
* broken references
* blank/incorrect pages

Fix discovered issues and recompile.

---

# 40. COMPLETION REPORT

After successfully generating and validating the black book, report:

* Final output location
* Number of chapters
* Number of figures/diagrams
* Number of tables
* Testing coverage included
* Compilation status
* Visual validation status
* Any intentionally blank or missing information

Do not claim successful validation unless the compiled output was actually inspected.
